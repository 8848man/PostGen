# Architecture Decision Records

> ADR-001~012는 기존 MVP 및 당시 후속 설계의 결정 기록이다. 새 제품 방향은 [Next Decisions](next/07-decisions.md)를 따른다. 충돌하는 경우 새 결정의 목표 상태가 우선하며 기존 구현 완료를 뜻하지 않는다.

결정 변경 시 이 파일의 해당 ADR에 새 상태와 이유를 기록한다. 관찰만으로 확정할 수 없는 실행 세부사항은 `검증 필요`로 둔다.

## ADR-001 — Skill을 제작 진입점으로 사용 (승인)

**맥락:** 첫 가설을 가장 짧게 검증해야 한다.  
**결정:** MVP에서는 사용자가 Codex CLI에서 Skill을 호출하고 CLI 대화에서 초안을 검토한다. HTML은 설정 전용이다. 제품의 다른 실행 호스트 목표는 ADR-011을 따른다.  
**결과:** 별도 콘텐츠 웹 앱은 만들지 않는다. Skill 발견·호출과 호스트 권한이 핵심 검증 대상이다.

## ADR-002 — 현재 폴더 연결 기록의 자동 탐색 (승인)

**결정:** 사용자는 기본 흐름에서 기록을 선택하지 않는다. 현재 작업 폴더와 연결된 지원 AI 기록을 자동 탐색한다. 다른 폴더의 기록은 자동 포함하지 않는다. 주제 선택은 기본 꺼짐의 고급 기능이다.  
**결과:** 기록 부족 시 빈 상태를 표시해야 한다. 기록 메타데이터 파서는 호스트별로 격리한다.

## ADR-003 — JSON Knowledge Package (승인된 설계 방향)

**결정:** 원본·파생·출처를 표현하는 버전형 JSON 계약을 사용한다. 그래프 DB는 도입하지 않는다.  
**결과:** 작은 초기 범위에 적합하며 복잡한 검색은 후속 평가로 남는다.  
**상태 (2026-11 사용자 확인):** 유효. 그래프 DB·온톨로지는 폐기한 것이 아니라 후순위로 보류한다. AI 초안 생성 → 승인 → 발행 엔진이 확정된 뒤 Obsidian 및 assetsManager의 DB 연동을 염두에 두고 저장 구조를 다시 검토한다.

## ADR-004 — 설정 HTML은 MVP 필수, 제작은 CLI (승인)

**결정:** HTML은 프리셋·프로필·레퍼런스·설정 채팅을 제공한다. 기본 제작에서 먼저 열지 않는다. AI의 설정 변경은 검증된 명령으로 적용한다.  
**결과:** 로컬 브리지와 Codex 채팅 연동은 MVP 검증 게이트다. 일반 UI에서 Skill Policy를 편집하지 않는다.

## ADR-005 — 저장과 내보내기 (승인된 기본값)

**결정:** 초안은 CLI에 표시한다. Markdown/HTML 파일은 사용자가 내보내기를 요청한 경우에만 생성한다.  
**결과:** 자동 파일 쓰기로 인한 의도치 않은 변경을 피하고 경로·덮어쓰기를 명확히 확인한다.

## ADR-006 — 후속 근거 백로그 (승인)

**결정:** MVP는 초안의 근거를 추적할 수 있어야 하지만 산출물·근거 문서의 장기 백로그 관리는 후속 Todo다.  
**결과:** Knowledge Package에는 안정적 ID와 출처 참조를 두되 저장소/상태 관리 UI를 만들지 않는다.

## ADR-007 — Codex 설정 채팅 연결 방식 (검증 완료)

**결정:** 로컬 Node 브리지에서 기존 Codex CLI 로그인과 `codex exec --ephemeral --sandbox read-only --output-schema`를 사용한다. 실제 구조화 설정 변경과 Windows 실행을 검증했다.  
**결과:** 호출마다 독립 실행하므로 채팅 문맥은 UI에서 제한된 최근 메시지만 전달한다. 인증 토큰을 읽거나 복사하지 않는다. 앱 서버는 MVP 의존성이 아니다.

## ADR-008 — 설정 UI 런타임 (구현)

**결정:** 브라우저 HTML/CSS/JavaScript와 Node.js 내장 HTTP 모듈을 사용한다. 외부 npm 패키지는 필요하지 않다.  
**결과:** 서버는 `127.0.0.1`에 임의 포트로 바인딩하고 세션 토큰·Origin 검사를 수행한다. 설정 화면은 Profile만 변경한다.

## ADR-009 — AI 실행 호스트와 입력 출처 분리 (2026-10-24 구현)

**맥락:** Codex와 Claude Code를 번갈아 사용하거나 일반 CLI 로그를 글의 재료로 삼아야 한다. 전체 로그를 모델에 한 번에 보내면 비용과 주제 혼입이 커진다.  
**결정:** 이 MVP 단계의 제작 호스트는 Codex Skill로 유지하고 입력은 제공자별 수집기로 정규화한다. 현재 폴더에 연결된 Codex·Claude Code 완료 대화와 Git 커밋 후보를 자동 발견한다. 일반 로그·문서는 사용자가 파일을 지정했을 때만 읽는다. 먼저 작은 출처 목록을 반환하고, 관련 `sourceId`를 지정해 기본 36,000자 한도 내에서 본문을 읽는다. 날짜는 관련성 판단의 보조 기준이다.  
**결과:** 대화 진술, Git 변경, 명시적 로그를 근거 유형별로 구분한다. 저장되지 않은 터미널 출력이나 접근 불가능한 호스트 기록은 복원하지 않는다. Claude Code 로컬 JSONL은 관찰된 형식으로 구현했으며 버전별 회귀와 실제 혼합 프로젝트 글 품질은 검증 필요다.

## ADR-010 — 한 명령 설치와 Skill 중심 사용법 (2026-10-27)

**맥락:** 복사 명령 여러 개와 수집기·설정 서버 사용법이 기본 제작 흐름보다 앞서 보이면 Skill의 장점이 가려진다.  
**결정:** 저장소 루트의 `node install.mjs`가 Postgen 폴더 전체를 사용자 Skill 위치에 설치한다. 새 설치는 공식 사용자 경로 `~/.agents/skills/postgen`을 사용하고, 기존 `~/.codex/skills/postgen` 설치가 있으면 같은 이름의 스킬을 중복 생성하지 않고 그 위치를 갱신한다. 설치기는 기존 대상이 Postgen인지 확인하며 다른 스킬은 덮어쓰지 않는다. 기본 사용법은 프로젝트 폴더에서 Codex CLI를 열고 `$postgen`으로 글을 요청하는 한 문장이다. 설정 화면과 파일 내보내기는 요청할 때만 안내한다.  
**결과:** Node.js 20 이상과 Codex 실행 환경은 여전히 필요하다. 출처 목록·ID·문자 한도는 내부 계약에 남기고 일반 README의 첫 사용 절차에서는 숨긴다. 기본 자동 탐색에서 관찰된 내부 `guardian` 승인 심사 세션은 사용자 작업 기록이 아니므로 후보에서 제외한다. 플러그인 배포와 패키지 관리자 설치는 별도 유통 단계다.  
**대안 (2026-11 사용자 확인):** React류 UI, Python 백엔드, 여러 복사 명령 설치를 검토했으나 패키징 부담과 추가 런타임 등을 고려해 채택하지 않았다(ADR-008의 Node 내장 모듈 기반 설정 화면과 함께).  
**상태:** 현재 MVP 방식은 유효하다. 가상 환경, 웹 호스팅, 프로그램 실행 시 자동 설치 중 개선 방식을 검토할 예정이며 선택은 미정이다. Next 로컬 제작·예약 화면은 `playwright-core` 때문에 별도 `npm install`이 필요하다(README).

## ADR-011 — 제품의 다중 AI 실행 호스트 지원 (2026-10-27, 제품 목표 확정)

**맥락:** Claude Code 기록을 Codex에서 읽는 것만으로는 Claude에서 Postgen을 직접 사용할 수 없다. 사용자는 Codex·Claude 및 향후 호환 AI에서 같은 제작 경험을 원한다.  
**결정:** Codex CLI는 첫 구현·검증 호스트로 유지한다. 제품은 Claude Code, Claude Cowork 및 계약을 만족하는 다른 AI 호스트에서도 Postgen 호출·초안 생성·수정·내보내기를 지원하는 것을 필수 목표로 한다. 입력용 Source Provider와 실행용 Host Adapter는 별도 확장점이다. 공통 지식·스타일·초안 계약은 특정 호스트의 인증·세션 위치·CLI 명령에 의존하지 않는다.  
**결과:** Claude Code 실행, Cowork의 실행 위치와 파일 접근, 기타 호스트의 기능은 각각 기술 검증과 수용 시험을 거쳐야 한다. `SKILL.md` 형식 호환성이나 기록 파서의 존재만으로 실행 지원을 표기하지 않는다. 현재 구현·설치 검증은 Codex에 한정된다.

## ADR-012 — 브라우저를 통한 채널별 등록 흐름 (2026-10-30, 설계 방향)

**맥락:** 블로그 초안을 X·Threads·네이버 블로그·티스토리에도 등록하고 싶다는 요청이 있다. 기존 MVP는 직접 발행을 제외했고, 네 채널의 편집 형식과 공개 설정은 서로 다르다.  
**결정:** 명시적 요청이 있을 때만 원본 초안에서 채널별 변형을 만들고, 사용자가 선택한 채널의 브라우저 편집기를 연다. 브라우저 조작은 로그인된 사용자 세션의 화면을 통해 편집기 채우기와 상태 확인을 수행한다. 각 채널의 계정·최종 내용·공개 범위를 사용자가 확인한 뒤에만 발행한다. 채널별 성공·실패·확인 불가를 독립적으로 기록하고, 발행 완료는 게시 URL이나 해당 채널의 명확한 완료 화면으로 검증한다.  
**결과:** 이 기능은 현재 MVP 이후의 별도 마일스톤이며 구현·실계정 시험은 미실시다. 공통 콘텐츠 계약과 Browser Publisher Adapter를 분리한다. 비공식 내부 API 호출, 로그인 정보 수집·저장, UI가 바뀐 상태에서 추측 클릭, 확인 불가한 발행의 자동 재시도는 설계에서 제외한다. 상세 흐름과 채널별 제약은 [Publication Flow Contract](15-publication-flow.md)를 단일 원본으로 둔다.
