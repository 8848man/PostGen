# Publication Flow Contract — 브라우저 등록 (후속 설계)

> 이 문서는 2026-10-30 당시의 설계 기록이다. 새 제품의 발행 경계는 [Next Workflow](next/03-workflows.md)가 우선한다. 새 방향([N-009](next/07-decisions.md), 2026-11-06 변경)에서는 사용자가 채널별 최종본과 공개 시각을 승인하면 플랫폼 예약 발행을 자동 등록한다. 플랫폼의 예약 확인과 공개 결과는 따로 확인·기록하며, 즉시 공개는 예약의 대체 수단으로 쓰지 않는다. 아래 본문의 '채널별 확인 후 발행' 흐름은 당시 설계다.

## 상태와 경계

이 문서는 ADR-012의 후속 제품 흐름을 정의한다. **2026-10-30 현재 설계만 완료했으며 브라우저 등록 구현과 실계정 검증은 하지 않았다.** 기존 Codex MVP의 기본 글쓰기·Markdown/HTML 내보내기 흐름은 유지한다. 등록은 사용자가 특정 초안과 채널을 명시할 때 시작한다. 로컬 HTML 설정 화면은 Style Profile용이며 게시 편집기가 아니다.

`BlogDraft → 채널별 PublicationVariant → 브라우저 편집기 준비 → 사용자 검토 → 채널별 발행 → 결과 확인`

콘텐츠 생성 호스트(Codex/Claude 등)와 게시 채널(X/Threads/네이버/티스토리)은 서로 다른 확장 축이다. `BrowserPublisherAdapter`는 호스트가 제공하는 브라우저 조작 기능에 의존하며, 지원하지 않는 호스트에서는 채널별 복사·붙여넣기용 결과와 수동 등록 안내를 제공한다. 브라우저 자동화가 가능하다는 사실만으로 로그인·게시 가능성을 보장하지 않는다.

## 사용자 흐름

1. 사용자가 검토한 초안에 대해 `X와 티스토리에 등록해줘`처럼 대상 채널을 지정한다. 미지정 채널은 추가하지 않는다.
2. Postgen이 각 채널에 맞는 버전을 만든다. 제목·본문·링크·이미지·태그·공개 범위 후보를 보여주고, 원본과 달라진 내용 및 빠진 근거를 표시한다. 중요한 사실 주장과 불확실성 표시를 다시 대조한다. 내부 세션 ID·로컬 경로·비밀 정보는 게시 본문으로 옮기지 않는다.
3. 사용자가 채널별 변형을 수정·선택한다. 계정, 공개 범위, 예약 여부처럼 채널 화면에서만 확정되는 값은 브라우저 편집기에서 확인한다.
4. 브라우저에 해당 채널의 로그인 세션이 있으면 편집기를 열어 제목·본문·태그 등 검증 가능한 필드를 채운다. 로그인이나 권한 확인이 필요하면 사용자에게 해당 화면을 넘긴다. 비밀번호·쿠키·토큰을 Postgen이 읽거나 저장하지 않는다.
5. 입력 후 편집기 화면을 다시 읽어 실제 값과 미리보기의 차이, 첨부 누락, 링크·서식, 대상 계정과 공개 범위를 확인한다. UI가 바뀌거나 필드가 모호하면 추측해 클릭하지 않고 사용자 편집으로 전환한다.
6. 채널마다 최종 미리보기를 보여주고 해당 채널의 발행 의사를 확인한 뒤 발행한다. 여러 채널을 선택해도 하나의 승인으로 일괄 게시하지 않는다. 사용자는 여기서 임시저장하거나 취소할 수 있다.
7. 게시 후 해당 채널의 완료 화면 또는 게시 URL을 확인한다. 검증되지 않은 클릭은 성공으로 보고하지 않는다. 일부 채널만 성공하면 성공한 URL과 미완료 채널을 분리해 보여준다.

## 채널 변환 및 편집기 매핑

| 채널 | 기본 변형 | 브라우저 입력·검수 지점 | 기술 검증 상태 |
| --- | --- | --- | --- |
| X | 짧은 단일 게시물 또는 순서가 있는 연속 게시물. 긴 글을 자동 절단하지 않고 핵심 주장·맥락·링크를 재구성 | 각 게시물의 길이·순서, 링크, 미디어, 게시 계정과 공개 상태 확인 | 공식 웹 작성·연속 게시 흐름 확인, Postgen 조작 미검증 |
| Threads | 500자 안의 요약 게시물을 기본값으로 생성. 긴 텍스트 첨부 기능은 해당 계정·화면에서 지원될 때만 선택 | 요약과 첨부 텍스트의 차이, 링크, 미디어, 계정 확인 | 공식 웹 게시·텍스트 첨부 안내 확인, Postgen 조작 미검증 |
| 네이버 블로그 | 제목·본문 단락·이미지·태그·카테고리 후보를 스마트에디터 ONE에 맞게 준비 | HTML 소스 삽입을 전제로 하지 않는다. 일반 텍스트 입력 뒤 서식·이미지·공개/검색/예약 옵션을 편집기에서 확인 | 공식 편집기·발행 안내 확인, Postgen 조작 미검증 |
| 티스토리 | 제목·본문·태그·카테고리를 준비하고, 계정에서 사용 가능한 에디터 모드에 맞춰 Markdown 또는 정리된 HTML을 선택 | 모드 전환 시 서식 손실 가능성을 확인. 미리보기, 공개/예약 옵션과 첨부를 확인 | 공식 에디터 모드 안내 확인, Postgen 조작 미검증 |

X 일반 게시물의 기본 글자 수는 280자이며 긴 글은 계정 구독에 따라 다르다. X 연속 게시물은 웹 작성기에서 추가한 뒤 한 번에 게시할 수 있다. [X 게시 안내](https://help.x.com/en/using-x/how-to-post), [X 연속 게시물 안내](https://help.x.com/en/using-x/create-a-thread). Threads의 일반 본문은 500자이며 텍스트 첨부는 최대 10,000자를 지원한다는 Meta 안내가 있다. 실제 계정의 편집기 노출은 검증이 필요하다. [Meta Threads 웹 안내](https://about.fb.com/news/2023/07/introducing-threads-new-app-text-sharing/), [Meta 텍스트 첨부 안내](https://about.fb.com/news/2025/09/attach-text-threads-posts-share-longer-perspectives/).

네이버 스마트에디터 ONE은 HTML로 글 작성하기를 지원하지 않고, 붙여넣은 숨은 HTML 태그가 오류를 일으킬 수 있다고 안내한다. 발행 시 카테고리·공개·검색·태그·시간 옵션을 확인한다. [네이버 미지원 기능](https://help.naver.com/service/5593/contents/15545?lang=ko&osType=PC), [붙여넣기](https://help.naver.com/service/5593/contents/15544?lang=ko&osType=PC), [발행 방법](https://help.naver.com/service/5593/contents/15541?lang=ko&osType=PC). 티스토리 에디터는 기본·Markdown·HTML 모드를 안내하며 모드 전환 시 서식이 달라질 수 있다. 티스토리 Open API는 종료돼 브라우저 편집기 경로를 우선 검증한다. [티스토리 에디터 모드](https://notice.tistory.com/2482), [Open API 종료 공지](https://notice.tistory.com/2664).

## 데이터 계약

`PublicationVariant/v1`은 `draftId`, `draftRevision`, `channel`, `format`, `title?`, `bodyParts[]`, `assets[]`, `tags[]`, `linkTargets[]`, `evidenceReview`, `warnings[]`를 가진다. `bodyParts[]`는 X의 연속 게시물처럼 순서가 필요한 채널에도 사용한다. `evidenceReview`는 원본 초안의 중요한 주장이 변형에서 유지·축약·제외된 이유와 검토 상태를 가리킨다. 민감한 로컬 출처 위치는 게시 페이로드에 넣지 않는다.

`PublicationAttempt/v1`은 `variantId`, `channel`, `requestedAccount`, `visibleAccount?`, `state`, `editorUrl?`, `postUrl?`, `lastVerifiedAt?`, `diagnostics[]`를 가진다. 상태는 `prepared → editor_open → filled → review_required → published`를 기본으로 하고, 각 단계에서 `cancelled`, `failed`, `unknown`으로 갈 수 있다. `published`는 채널 완료 화면 또는 게시 URL을 확인한 경우에만 사용한다. 저장 위치·보존 기간은 구현 전 별도 결정한다. 이 계약은 장기 산출물·근거 백로그 시스템의 구현을 전제하지 않는다.

## 브라우저 조작 계약

- `openEditor(channel)`, `readEditorState()`, `fillVariant(variant)`, `saveDraftIfSupported()`, `publishAfterApproval()`, `verifyPublication()`을 채널 Adapter의 논리적 동작으로 정의한다. 실제 셀렉터나 화면 좌표는 공개 계약에 넣지 않는다.
- 브라우저의 현재 접근 가능한 UI에서 계정·필드·버튼을 식별한다. 숨겨진 내부 요청 재생, 세션 쿠키 추출, CAPTCHA 우회는 하지 않는다. 로그인·추가 인증은 사용자가 수행한다.
- `fillVariant` 후 읽은 편집기 값이 요청과 다르면 발행을 중단하고 차이를 보여준다. 예약·공개·댓글/검색 등 채널 옵션은 표시된 값만 신뢰한다.
- 발행은 **채널별·게시물별** 사용자 확인 후 수행한다. X 연속 게시물처럼 하나의 편집기에서 묶어 게시하는 경우에는 전체 순서와 각 본문을 함께 확인한다.
- 발행 클릭 뒤 결과가 불명확하면 `unknown`으로 두고 동일 내용을 자동 재시도하지 않는다. 사용자가 해당 계정의 게시 목록을 확인한 뒤 재개한다.

## 구현 전 검증 게이트

1. 네 채널의 현재 웹 편집기에서 로그인 세션 접근, 필드 식별, 임시저장 가능 여부와 발행 완료 신호를 각각 확인한다. 테스트 게시 없이 확인 가능한 범위와 실제 게시가 필요한 범위를 분리한다.
2. 채널별 변환의 길이·서식·근거 보존을 합성 초안으로 시험한다. 네이버 붙여넣기 서식, 티스토리 모드 전환, X 연속 게시물과 Threads 첨부는 별도 사례로 둔다.
3. 로그인 만료, 계정 불일치, CAPTCHA, 제한·오류 화면, UI 변경, 네트워크 중단, 중복 게시 가능성을 실패 주입한다. `unknown` 상태에서 자동 재발행하지 않는지 확인한다.
4. 실제 계정 시험은 채널별 발행 승인과 시험용 콘텐츠·공개 범위를 구체적으로 정한 뒤 수행한다. 성공/실패/부분 성공을 URL 등 화면 증거와 함께 보고한다.
